# Macro audit after 0.24

**Keep `unless` as optional surface sugar.** Its two branches stay lazy.
The example puts a division by zero in each discarded branch in turn.
An ordinary eager function would need callers to wrap both branches in
closures to obtain the same behavior. In short expressions, plain
`if ... then ... else ...` is still easy to read.

**Keep the shared `timedDrill` template if the wording is a project
convention.** It builds two fields from the exercise inputs, and both lessons
reuse it. A one-to-one wrapper around `Drill` adds a declaration and an
`expand` at each call. Ordinary pure data assembly, including `timedDrill`
itself, can also be implemented as a function. Its role here is to exercise
macro scope and reuse with a realistic example.

**Leave the parser guards explicit.** The audit script finds 29 instances
of `if parseFailed result then result else …` in the Nail parser. A hygienic
template can preserve lazy continuation evaluation. With the parentheses
normally needed around a continuation, the representative call takes
6 whitespace tokens versus 7 for the original form. After including the
21-token macro declaration, the rough saving over all 29 sites is 8 tokens.
That estimate does not include indentation or a module import. The script
checks the proposed template on both success and error branches. The
repeated error propagation in `coreRead` would need binding-aware syntax
to replace it cleanly. A fixed expression template cannot introduce a named
binding for arbitrary caller code while preserving hygiene.

The lesson comparison was executed against the generated data and HTML.
It has not been tried with a pupil.

## 2026-11-17 — Macro experiment against NailLang 0.49

**Rule (pre-1.0): use a macro only when it removes more complexity than it introduces.** No source/ABI compatibility obligation prevents rewriting or removing earlier mechanisms. Prefer plain Nail functions for transformations that require neither syntactic capture nor laziness; reserve macros for compile-time syntax transformation, hygienic code generation, and lazy control flow.

### Tested: `parseContinue` in the self-hosted Nail parser

A draft [experiment](https://github.com/Spyryto/NailLang/pull/12) replaced **11** occurrences of the parser's `if parseFailed result then result else continuation` with a hygienic template macro:

```nail
macro parseContinue checked next = quote (
  if parseFailed ( unquote checked ) then unquote checked else unquote next
) ;
```

- Unmodified `stdlib.nail`: **58,679 characters**.
- Experimental `stdlib.nail`: **58,913 characters** (**+234**, not a reduction).
- The experimental branch **passed the full Haxe, JavaScript and PHP CI**, including self-hosted compiler fixed-point and source-free bootstrap tests. This verifies compatibility of that experiment's behavior with the tested cases, **not** a performance improvement or byte-for-byte identity with an earlier release image.
- The macro runs at compile time and preserves *lazy* evaluation of the success continuation. But `quote`/`unquote`, `expand`, parentheses, and explicit hygiene add enough ceremony to outweigh the removal of the repetitive guard. An unquoted argument used twice may also be evaluated twice if callers pass a computation instead of a pre-bound value.
- **Decision: do not merge the implementation change.** Leave the explicit guards rather than add an abstraction with a negative net simplification.

### Where the existing machinery earns its keep

1. **Expression/template macros:** introduce control flow whose arguments must not be evaluated eagerly (as with `unless`), or compact domain-specific expressions where a plain function cannot give the same semantics.
2. **Nail-written syntax transformers:** build declarations from `Syntax`, especially record/ADT constructors and accessors, when output is validated by the static checker and reproducible in the source-free compiler. Nail already has a record declaration transformer; replacing the independent Haxe oracle would require proving a safe bootstrap architecture, not merely deleting code.
3. **Ordinary functions first:** parsing helpers, record/sum AST builders, list transformations, and numeric relations should be functions or existing compiler passes unless a macro gives a measured benefit.
4. **Current limitation:** template macros are expression-oriented; typed procedural transformers currently append *fresh definitions* rather than seamlessly rewriting arbitrary subexpressions/AST declarations. Introducing name bindings into caller syntax while preserving hygiene, type provenance and source positions is still a substantial design problem.

### Admission test for a future macro refactor

For each candidate, record **net source size (Haxe + Nail), number of duplicated rules eliminated, generated bytecode/semantics, diagnostics, compile-time cost and bootstrap fixed-point results**. Validate on Haxe, Node and PHP. Keep the macro only if it clearly improves cohesion or removes a substantial implementation path without sacrificing the small, readable core. Negative experiments should remain documented rather than silently becoming permanent dependencies.


## 2026-11-17 — Unified record and sum lowering (PR #13)

This is the first **implementation-level** follow-up to the audit. The production Nail-written compiler now lowers `RecordType` and `SumType` to the **same ordinary declaration syntax** before invoking `compileForm`. Previously records used a Syntax transformer and sums had a separate special-case bytecode emitter. Both now use `expandTypeDeclarations : Syntax -> Syntax` (conceptual signature) and share `makeConstructor` for runtime record representation and `fieldSyntax` for projections.

**Bootstrap boundary:** the independent Haxe parser, `RecordLowering`, `SumLowering` and `BytecodeCompiler` still exist intentionally. They are required to create the initial standard-library image and to provide a separate oracle that catches self-hosting mistakes. Deleting those now would require a trustworthy stage-0 image and reproducible two-stage bootstrap. In the Haxe evaluator, executing a type declaration and executing an ordinary definition now share a single code path after Haxe lowering.

**Why no `quote` macro?** The current template macro system expands *expressions*, not arbitrary top-level `RecordType`/`SumType` forms. The procedural transformer contract can emit new typed declarations, but making it rewrite built-in type forms inside the compiler would add binding/source-contract machinery and threaten the bootstrap boundary. Here **ordinary Nail functions over first-class Syntax** are smaller, clearer, and already exercise the metaprogramming representation. Do not force the current macro mechanism into a role it does not yet support.

**Production-source measurement (against PR base):** `stdlib.nail` **58,679 → 58,764 bytes/characters (+85)**; `Vm.hx` **29,552 → 29,112 (-440)**. Net for these two production files: **355 characters fewer**, and more importantly one instead of two Nail bytecode generation paths. These figures deliberately **exclude the new test sources and CI wiring**, which increase repository size. No runtime speedup is claimed.

**Validation:** a dedicated Haxe/Node/PHP differential test checks the generated declarations against the independent Haxe AST oracle, confirms no type declarations survive lowering, checks bytecode equality and sample runtime results, and exercises mixed records, ADTs, nested values, macro expansion and modern `Int` syntax. Existing bootstrap fixed-point, module ABI, and numeric tests are also run. Typed source validation remains the responsibility of `TypeChecker` on the original declarations, not the lowered executable forms.

Next possible experiments: separate the stage-0 compiler from normal runtime compilation explicitly; expand the procedural transformer API only if a real requirement shows that today's expression-only templates and declaration generators cannot remove substantial duplicated logic.


## 2026-11-17 — Exactly one macro expansion pass (PR #16)

The Nail-written compiler previously expanded template macros twice when using
the modern or exact source entrypoints: once **before** rewriting numeric
syntax, and again in `compileSyntax` before generating bytecode. The second
pass normally found no markers, but still traversed the entire transformed
program to determine that.

`compileExpandedSyntax` now handles already-expanded `Syntax`, with all
record and ADT declaration lowering and bytecode generation unchanged. The
public `compileSyntax` remains responsible for accepting *raw* Syntax and
expanding its macros exactly once. Modern/exact source and module-resolved
compiler paths call the internal helper after their first expansion.

**Measured by an instrumented `HostFunction` probe (not by presumed
idempotence):** direct plain, modern, and exact compilation each invoke
`macroExpandSyntax` **once**, while the module-resolver path invokes it
**zero times** inside the Nail compiler because Haxe already expanded the
imports. The public raw Syntax API invokes it **once**.

The dedicated Haxe/Node/PHP suite also compares generated bytecode with
the independent Haxe seed compiler, and checks hygienic macros, nested
macro calls, records, the exact numeric dialect and imported macro modules.
For comparisons involving the modern numeric dialect, imported modules must
declare their modern language version explicitly: mixing an unversioned
macro module's numeric literals with a versioned importer produces
inconsistent semantics across compiler paths, an **existing** limitation to
address in a separate language-module contract.

**Strength:** the existing host macro mechanism composes with Nail-written
parsing and code generation when each compilation stage has a clear
precondition. **Weakness:** macro-aware source-free compilation still depends
on Haxe `MacroExpander` and AST adapters; rewriting that component in Nail
would be a substantive hygiene and bootstrap project. This refactor saves
a full redundant AST scan, **not** total source code; no throughput gain is
claimed without a separate benchmark.

## 2026-11-17 — Imported macro dialect fix (issue #17)

**Rule:** imported template macro modules must declare the caller's *exact*
`nail X.Y ;` version if the caller is versioned. If the caller is unversioned,
so must the module be. Experimental `# nail: 0.29` Exact is still segregated
from default unversioned Float. This applies to **transitive** imports too.

The Haxe reference parser previously checked only the legacy Exact flag,
allowing an unversioned macro's Float-typed literal to enter a modern caller
while Nail's self-compiler rewrote the same literal to `Int`. The shared
`MacroModuleDialect` validator now rejects that ambiguity **before**
template expansion and emits a named, actionable diagnostic. Matching numeric
headers preserve existing hygiene and compiler bytecode parity.

The decision deliberately favors an explicit compilation contract, not
automatic cross-version macro compatibility or an extra conversion pass.
