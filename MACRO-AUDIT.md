# Macro audit after 0.24

**Keep `unless` as optional surface sugar.** Its two branches stay lazy.
The example puts a division by zero in each discarded branch in turn.
An ordinary eager function would need callers to wrap both branches in
closures to obtain the same behavior. In short expressions, plain
`if ... then ... else ...` is still easy to read.

**Keep the shared `timedDrill` template if the wording is a project
convention.** It builds two fields from the exercise inputs, and both lessons
reuse it. A one-to-one wrapper around `Drill` adds a declaration and an
`expand` at each call. Ordinary pure data assembly, including `timedDrill`
itself, can also be implemented as a function. Its role here is to exercise
macro scope and reuse with a realistic example.

**Leave the parser guards explicit.** The audit script finds 29 instances
of `if parseFailed result then result else …` in the Nail parser. A hygienic
template can preserve lazy continuation evaluation. With the parentheses
normally needed around a continuation, the representative call takes
6 whitespace tokens versus 7 for the original form. After including the
21-token macro declaration, the rough saving over all 29 sites is 8 tokens.
That estimate does not include indentation or a module import. The script
checks the proposed template on both success and error branches. The
repeated error propagation in `coreRead` would need binding-aware syntax
to replace it cleanly. A fixed expression template cannot introduce a named
binding for arbitrary caller code while preserving hygiene.

The lesson comparison was executed against the generated data and HTML.
It has not been tried with a pupil.

## 2026-11-17 — Macro experiment against NailLang 0.49

**Rule (pre-1.0): use a macro only when it removes more complexity than it introduces.** No source/ABI compatibility obligation prevents rewriting or removing earlier mechanisms. Prefer plain Nail functions for transformations that require neither syntactic capture nor laziness; reserve macros for compile-time syntax transformation, hygienic code generation, and lazy control flow.

### Tested: `parseContinue` in the self-hosted Nail parser

A draft [experiment](https://github.com/Spyryto/NailLang/pull/12) replaced **11** occurrences of the parser's `if parseFailed result then result else continuation` with a hygienic template macro:

```nail
macro parseContinue checked next = quote (
  if parseFailed ( unquote checked ) then unquote checked else unquote next
) ;
```

- Unmodified `stdlib.nail`: **58,679 characters**.
- Experimental `stdlib.nail`: **58,913 characters** (**+234**, not a reduction).
- The experimental branch **passed the full Haxe, JavaScript and PHP CI**, including self-hosted compiler fixed-point and source-free bootstrap tests. This verifies compatibility of that experiment's behavior with the tested cases, **not** a performance improvement or byte-for-byte identity with an earlier release image.
- The macro runs at compile time and preserves *lazy* evaluation of the success continuation. But `quote`/`unquote`, `expand`, parentheses, and explicit hygiene add enough ceremony to outweigh the removal of the repetitive guard. An unquoted argument used twice may also be evaluated twice if callers pass a computation instead of a pre-bound value.
- **Decision: do not merge the implementation change.** Leave the explicit guards rather than add an abstraction with a negative net simplification.

### Where the existing machinery earns its keep

1. **Expression/template macros:** introduce control flow whose arguments must not be evaluated eagerly (as with `unless`), or compact domain-specific expressions where a plain function cannot give the same semantics.
2. **Nail-written syntax transformers:** build declarations from `Syntax`, especially record/ADT constructors and accessors, when output is validated by the static checker and reproducible in the source-free compiler. Nail already has a record declaration transformer; replacing the independent Haxe oracle would require proving a safe bootstrap architecture, not merely deleting code.
3. **Ordinary functions first:** parsing helpers, record/sum AST builders, list transformations, and numeric relations should be functions or existing compiler passes unless a macro gives a measured benefit.
4. **Current limitation:** template macros are expression-oriented; typed procedural transformers currently append *fresh definitions* rather than seamlessly rewriting arbitrary subexpressions/AST declarations. Introducing name bindings into caller syntax while preserving hygiene, type provenance and source positions is still a substantial design problem.

### Admission test for a future macro refactor

For each candidate, record **net source size (Haxe + Nail), number of duplicated rules eliminated, generated bytecode/semantics, diagnostics, compile-time cost and bootstrap fixed-point results**. Validate on Haxe, Node and PHP. Keep the macro only if it clearly improves cohesion or removes a substantial implementation path without sacrificing the small, readable core. Negative experiments should remain documented rather than silently becoming permanent dependencies.
